ADR-001: Multi-tenant platform built from SLMS360 and ToddlersApp

Status
Proposed
Date
2026-09-24
Deciders

Context

Opsyra is a new SaaS for small businesses. It combines the admin modules of SLMS360 and ToddlersApp, and CRM will be added later. Neither product fits as-is:

  • SLMS360 has the strongest HRMS, including the v2.5.0 work shipped this month (RBAC, approvals with an L2 gate, salary and attendance hubs, setup wizard, subscription enforcement, US payroll). It runs one deployment per client: app → client code → that client's endpoint. None of its tables carry a tenant key.
  • ToddlersApp already runs as one deployment with a single endpoint that resolves the client per request, and it isolates clients inside that deployment.
  • Brainstormer sells in the US, UK, Oman and Pakistan, so client data should stay in its own country.
  • Small-business tenants are numerous and small. A database per tenant would cost more to operate than it's worth at this size.
  • The v2.5.0 security review removed six SLMS360 modules because any logged-in staff member could reach data they shouldn't. The new product has to rule out that class of bug by design.

Decision

  1. New standalone codebase. Opsyra is a new repository. SLMS360 and ToddlersApp are not modified. Code is copied from read-only reference clones and repurposed, and each module's origin is recorded with its source commit.
  2. One deployment per country (us, uk, om, pk) from one codebase. Country is configuration, never a fork.
  3. One shared PostgreSQL database per country. All clients in that country are tenants in the same database, isolated by tenant_id.
  4. Two-layer isolation. A global query scope in the app, plus Postgres row-level security keyed on app.tenant_id. A missed filter in code still can't return another tenant's rows.
  5. Tenant resolution is ported from ToddlersApp. The user experience stays the same: the app asks for a client code, and a small global directory maps that code to the right country endpoint.
  6. Per-country platform tables for tenants, subscriptions, plans and feature flags, and payroll tax tables. These replace SLMS360's subscription bridge and the planned cross-deployment Tax Table Service.
  7. Escape hatch for large clients. The resolver returns a database connection, so a large tenant can move to a dedicated database without code changes.

Where both products have the same module, the inventory step compares them and recommends one. They are never merged silently.

Isolation rules every module must follow

  1. Every tenant table has tenant_id, including pivot, log, attachment and settings tables. Indexes lead with it, and unique constraints include it.
  2. Scoping is automatic through a BelongsToTenant trait. Any opt-out is explicit, easy to search for, and code-reviewed.
  3. RLS is enabled on every tenant table. Middleware and queued jobs set app.tenant_id.
  4. Every submitted foreign ID is validated within the tenant.
  5. Every action checks role and ownership, not just login. This is the issue class the v2.5.0 review found.
  6. Cache keys, file storage paths, exports and queued jobs carry the tenant.
  7. A cross-tenant test (log in as tenant A, attack tenant B's data on every route) runs in CI and blocks merges.

Alternatives considered

Database per tenant

Strongest isolation, and the SLMS360 code would work unchanged. Rejected as the default because operating hundreds of small-business databases costs too much. Kept as the escape hatch for large clients.

One global deployment

Simplest to run, but it puts every country's client data in one place and makes each outage global. Rejected because of data residency.

Shared database on MySQL

Matches the current stack, but MySQL has no row-level security, so isolation would rest entirely on application code. Rejected in favor of Postgres.

Evolve SLMS360 in place

Avoids a new repository, but it puts an existing product and its clients at risk. Rejected: the originals stay untouched.

Consequences

Positive

  • Four deployments to run instead of one per client
  • Client data stays in its own country
  • Isolation is enforced by the database as well as the app
  • Tax tables and subscriptions live in one place per country
  • SLMS360 and ToddlersApp clients are unaffected

Costs

  • SLMS360 modules need a tenant_id retrofit
  • MySQL-specific SQL must be converted to Postgres
  • Bug fixes may need applying in three codebases for a while
  • The global directory is a shared dependency; keep it tiny and cached

Delivery plan

  1. Create reference clones and a module inventory. Review checkpoint.
  2. Scaffold the app and build the tenancy core, global directory and cross-tenant test harness. Review checkpoint.
  3. Port modules one at a time, RBAC and HR core first, each passing the isolation tests before the next starts.
  4. Add country configuration, feature flags and templates for the four deployments.
  5. Design CRM fresh on top of the tenancy core.

Open questions

  • Which SLMS360 branch is the source of truth for v2.5.0: brainstormertech or alis?
  • ToddlersApp's backend stack and exact tenancy mechanism. The inventory step will confirm both.
  • Hosting region for the Oman and Pakistan deployments, and whether local regulators require in-country hosting.
  • Whether existing SLMS360 clients will be offered migration to Opsyra, or stay on SLMS360.
