Opsyra Staff App API

What the staff mobile app needs from the Opsyra servers: signing in, clocking in and out, home-care visits, payslips and tasks.

Version 1.0 Date 30 September 2026 For the mobile app developer Contact BrainStormers Technologies

Overview

Opsyra runs one server per country. Each company's data lives only on its own country's server. The app talks to two places:

Central (lookup only)https://opsyra.brainstormertech.com/api
Turns the company code a person types into the address of their country server. Called once, at first sign-in.
Country server (everything else)https://us.opsyra.brainstormertech.com/api
The United States server today. The UK, Oman and Pakistan will get their own. Never hard-code this; use the address Central returns.

Every endpoint in this guide acts only for the signed-in person. Someone can only see and change their own attendance, visits, payslips and tasks. The server checks this on every call, so the app doesn't need its own permission logic. /auth/me also returns the person's permissions if you later add manager screens.

Requests and responses

TopicRule
HeadersSend Accept: application/json on every request. Without it, validation errors come back as a web redirect instead of JSON. Send Content-Type: application/json with a JSON body on POSTs.
Signed-in callsAuthorization: Bearer <token> using the token from /auth/login.
MethodsReads are GET with query parameters. Everything that changes something is POST, including some lookups by id (for example /payroll/payslips/show).
Response shape{"status": true, "message": "…", "data": …}. Show message to the person after an action; it's written for them.
DatesPlain dates are YYYY-MM-DD in the company's local calendar (a "day" at work means the local day).
TimesAttendance and visit times are ISO 8601 with the company's local offset, e.g. 2026-09-30T09:00:00-05:00. Responses also give the timezone name. Record timestamps elsewhere (payroll, created_at) are UTC, e.g. 2026-09-27T00:05:51.000000Z.
MoneyNumbers in the currency's main unit (dollars, not cents), with a currency code next to them. They can have decimals.
LocationSend latitude and longitude as decimal degrees and accuracy_m as whole metres. Location is never a reason to refuse a clock-in or check-in: if the person is far away or has no signal, the action still succeeds and is flagged for a manager to review.

Signing in

  1. Look up the company. The person types their company code (for example brains). Call Central's POST /resolve. Store the returned api_base_url with the code, and use it for everything below.
  2. Sign in. POST {api_base_url}/auth/login with the code, email and password. Store the token in the Keychain (iOS) or Keystore (Android).
  3. Check for a forced password change. If must_change_password is true, show only a change-password screen and call /auth/change-password. Until then, every other call returns 403 with password_change_required.
  4. Load the person. GET /auth/me, then GET /attendance/today. Its attendance_mode decides the home screen (see below).

Tokens don't expire today. They end when the person signs out, changes their password on another device, leaves the company, or the company is suspended. Whenever any call returns 401, clear the token and go back to sign-in.

"Forgot password" sends an email whose link opens the Opsyra website, so the app only needs to call /auth/forgot-password and show the message. The reset itself happens in the browser.

Errors and limits

StatusMeaningWhat the app should do
401{"message": "Unauthenticated."}. Missing, wrong or revoked token.Clear the token; show sign-in.
403{"status": false, "message": "…"}. Not allowed: account not active, company suspended, or not your record. With "password_change_required": true the person must change their password first.Show the message. For password_change_required, open the change-password screen.
404Unknown company code (Central) or record not found.Show the message.
409{"status": false, "message": "…"}. A rule refused the action, e.g. "You're already clocked in." or "This visit isn't due now — it's planned for 30 Sep, 14:00."Show the message as it is. Don't retry automatically.
422Validation. {"message": "…", "errors": {"field": ["…"]}}. Wrong sign-in details also come back as 422 on email.Show each error under its field.
429Too many attempts. The message says how many seconds to wait.Show the message; disable the button for that long.

Limits: 30 requests a minute per device for sign-in, forgot-password and the Central lookup. Five failed passwords in a minute for one account locks that account's sign-in for a minute.

Which screens a person gets

Each person has an attendance_mode, set by HR and returned by /attendance/today and /attendance/my-schedule:

schedule

Office and shift staff. Home screen: a clock in / clock out button, today's hours, this month's attendance.

visits

Home-care workers. Home screen: today's client visits, each with check in / check out. Clock in/out is refused for them.

not_tracked

Attendance is off for this person. Hide attendance; show pay, tasks and profile.

Everyone gets payslips, salary queries, tasks and their profile.

POST/attendance/clockSigned in

Clock in or out. Leave out type and the server does the next thing (in if not clocked in, otherwise out).

FieldRules

branch_idOptional. One of the person's branches from /attendance/today; ask only if they have more than one.
latitude, longitudeOptional but please send; both or neither.
accuracy_mOptional, whole metres.
deviceOptional, e.g. "iPhone 15 / iOS 18.1".

Response 201

The updated day object plus "punch_type": "in" or "out". The message is "Clocked in." or "Clocked out.", with "You're 850 m from the branch, so HR will review this." added when the location was outside the branch's radius.

Refused (409)

"You check in at each visit instead — open today's visits." (visits mode) · "Attendance isn't tracked for you. Ask HR if that's wrong." · "You're already clocked in." · "You're not clocked in."

Home-care visits

For people in visits mode: caregivers who travel to clients. They check in and out at each client's address instead of clocking in. They're paid for verified visit time.

Privacy. A visit's location is a client's home. Show the address and access notes only on the visit screen, never cache them longer than the day needs, and don't show them in notifications on a locked screen.

Status values

FieldValues
Day statusopen (today, not settled yet), present, half_day, absent, on_leave, remote, day_off, holiday. leave_paid is true/false for leave, otherwise null.
Day sourceapp, web, system (set by the close-out), manual (entered by HR).
Visit statusplanned, in_progress, completed, missed, cancelled.
Visit review_statusnull (nothing to check), needs_review (flagged by location), accepted, rejected. Show review_note when rejected.
Person statusactive, pending (approved, not started yet; can use the app for onboarding tasks). People awaiting approval or who have left can't sign in.
Correction / query statusopen, approved, rejected.
Task statustodo, in_progress, done, skipped.

Not available yet

Plan the app so these can slot in later. Tell us which ones you need first.

  • Leave requests (holiday and sick leave with balances). This module is next in the build plan. Until then, staff use "ask to fix a day" with requested_status: "on_leave".
  • Push notifications (visit changes, approvals, payslip ready). There's no device-registration endpoint yet.
  • Changing your own photo or profile details. HR does this in the web app for now.
  • Locking an account to one phone. Not enforced; the device and device_name you send are only recorded.
  • Offline clocking. Every clock-in or check-in is recorded at the moment the server receives it. Don't queue taps to send later: a queued tap would be stamped with the wrong time.
  • Token expiry and refresh. Tokens don't expire today. If we add expiry, expired tokens will return 401, which you already handle.

Testing

  • Server: https://us.opsyra.brainstormertech.com/api is our live test system. Resolve codes through Central as described above.
  • Test accounts: we'll set up a test company for you with one office worker (schedule mode) and one caregiver (visits mode) with visits planned for each day, and send the sign-in details separately. Please don't use real people's data in tests.
  • Public demo: company code demo is a shared sample company that's reset every night. Its sign-in is shown on the Opsyra website. It's useful for a quick look, but some actions are locked there.

  • GET /staff/offboard/pending-approvals, POST /staff/offboard/approve, /staff/offboard/reject. People leaving.
  • GET /attendance/corrections/list, POST /attendance/corrections/approve, /attendance/corrections/reject. Fix-a-day requests from the team.

Attendance and visits (managers and coordinators)

  • GET /attendance/dashboard, /attendance/daily, POST /attendance/person-month, /attendance/mark, /attendance/staff-mode
  • Working hours: /attendance/schedules/list|create|update|delete|assign|assignments|people; holidays: /attendance/holidays/list|create|update|delete; rules: /attendance/policy, /attendance/policy/update
  • Visit board: GET /visits/day, /visits/caregivers, /visits/review-queue; POST /visits/create|update|cancel|set-times|review
  • Clients and plans: /visits/locations/list|create|update|delete, /visits/plans/list|create|update|delete

People and HR

  • Staff: POST /staff/list|index|limited-list|create|update|status-update|offboard|cancel-offboarding|active-direct-reports|update-avatar|clear-device-id, GET /staff/eligible-managers
  • GET /hr/dashboard, /teams/list, POST /teams/members
  • Checklists: /checklists/list|show|start|add-task|cancel, /checklist-templates/list|create|update|delete
  • Setup lists: /branches/*, /departments/*, /designations-management/*, /departure-reasons/*
